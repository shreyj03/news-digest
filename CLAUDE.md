# News Digest

A multi-user website: sign up, add topics, and each morning it fetches and shows fresh articles matched to those topics, on your own chosen delivery time/timezone. Anonymous visitors see a live demo account read-only.

**Stack:** React/TypeScript/Vite frontend (`web/`), Express/TypeScript API (`api/`), standalone ingestion script (`ingest/`), Postgres (`db/`).

**Status: live and multi-user (Milestone 8 shipped 2026-08-28).**
- Frontend: https://news-digest-web.onrender.com (Render static site)
- API: https://news-digest-api-a1q4.onrender.com (Render free web service)
- Database: Neon project `news-digest` (`wild-brook-94486900`)

**Accounts & demo.** Real email+password accounts — scrypt-hashed (`api/src/auth.ts`, Node's built-in `crypto.scrypt`, no new dependency), DB-backed bearer sessions (`sessions` table, revocable by deleting a row). Replaces the earlier single shared `SITE_PASSWORD` model entirely. `topics`/`tickers` are `user_id`-scoped with `UNIQUE(user_id, name)`/`UNIQUE(user_id, symbol)`. Anonymous visitors (no session) see whichever account `DEMO_USER_EMAIL` points at (currently `jainshrey2004@gmail.com`, still an ordinary account — not special-cased in code), read-only. The pre-existing single-owner data was migrated to a "claim"-able bootstrap row (`password_hash IS NULL`, an email that already exists but has no password); signing up with that same email sets the password instead of rejecting as a duplicate — this is the one and only migration path, exercised by fresh local `db/seed.sql` setups too, not a one-off script.

**Scheduling — genuinely per-user, not a shared cron.** `ingest.ts`/`match.ts` now require `TARGET_USER_ID` (no global mode left at all — every fetch is scoped to one user's own topics). `POST /api/tick` loops over every `digest_enabled` user each run and, per user: fetches+matches their topics ~5 minutes before their own chosen local `digest_time`/`digest_timezone` (`Intl.DateTimeFormat`, DST-correct), then emails them at it — each step gated by `last_fetch_date`/`last_digest_sent_date` so a re-trigger within the same local day no-ops. This design was a mid-build correction: the first pass kept one shared daily ingest with only delivery *time* varying per user, which the user flagged as wrong once different users have different topics. See DECISIONS.md's 2026-08-28 entry for the full reasoning and a real bug caught along the way (`pg` returns `DATE` columns as JS `Date` objects, not strings — silently broke the dedup comparison until a global `pg.types.setTypeParser` override in `api/src/db.ts` fixed it).

**Tick trigger: cron-job.org (free), not GitHub Actions' `schedule` — live and verified (2026-08-28).** The owner's 7am digest didn't arrive; investigation found `.github/workflows/tick.yml`'s `schedule: cron: "*/5 * * * *"` had fired exactly once in the ~22 hours since deploy, and that one firing landed 51 minutes before the send window — GitHub silently deprioritizes/drops high-frequency `schedule` events on lower-traffic repos, confirmed via `gh run list`/Render boot logs. Fixed by removing the `schedule` trigger from `tick.yml` entirely (kept `workflow_dispatch` for manual runs) and pointing [cron-job.org](https://cron-job.org) at `POST /api/tick` with the same `Authorization: Bearer FETCH_SECRET` header, every 5 minutes. A second, unrelated bug compounded the miss: an earlier manual verification run had left `last_fetch_date`/`last_digest_sent_date` set to today's date, which would have blocked a correctly-timed tick from sending anyway — cleared via direct SQL, one-time cleanup, not a recurring issue. Recovered the owner's missed digest live by briefly bumping their `digest_time` to the next few minutes, clearing the flags, triggering `tick.yml` manually twice (fetch window, then send window — confirmed `sent: true`), then restoring `digest_time` to 07:00. See DECISIONS.md's 2026-08-28 "Tick scheduling" entry for the full reasoning and alternatives considered (Render Cron Job rejected — no free tier).

**Verified end-to-end, live, not just locally:** the production Neon DB migration (bootstrap owner row + `user_id` backfill + new constraints) applied via a single Neon MCP transaction; `DEMO_USER_EMAIL` set on the live API and confirmed anonymous `GET /api/topics`/`/api/feed` show the real migrated data read-only while mutations still 401; `tick.yml` manually triggered twice against production (once landing in the pre-fetch window, once in the send window) and confirmed via direct DB checks (`last_fetch_date`/`last_digest_sent_date` set correctly, one fetch + one send, not both at once) and via the actual delivered Gmail message (real fresh article content, arrived at the exact tick timestamp). Locally verified before that: signup-claims-bootstrap-row, multi-user isolation (a second account starts empty, can't touch the first's data), the frontend's demo banner/login-signup form/digest-settings panel/new-account empty state, all via Playwright.

The owner has since signed up through the live UI and claimed the account themselves (their own password, never handled by Claude). A welcome email (`sendWelcomeEmailForUser()`, same visual system as the digest email, a feature tour instead of matches) now sends once on signup, including the claim path.

**Email provider: Resend → Brevo — live and verified (2026-08-28).** Resend's free/sandbox tier only delivered to the Resend account's own exact email — confirmed live, even `jainshrey2004+test@gmail.com` (same inbox, Gmail plus-addressing) got a 403, silently breaking email for any real user who wasn't the account owner. Switched to Brevo (`sendEmail()` in `api/src/index.ts`, `BREVO_API_KEY` + `DIGEST_EMAIL_FROM` replacing `RESEND_API_KEY`, see DECISIONS.md), sender verified as `notification.newsdigest@gmail.com` (a dedicated address, not the owner's personal one). **Confirmed live with a genuinely different recipient** — signed up `jainshrey2004+brevotest@gmail.com` (a distinct address, not the account owner's), and both the welcome email and (via a manually-triggered `tick.yml` run) the digest email arrived in that inbox, not spam — proving Brevo actually sends to arbitrary recipients where Resend couldn't. Test accounts deleted after confirming with the user.

**Forgot-password flow — live and verified (2026-08-28).** The owner forgot their own password after setting it; rather than Claude touching it, built the real flow: `POST /api/forgot-password` (`{email}`, always the same generic response either way, no email enumeration) and `POST /api/reset-password` (`{token,password}`, single-use 1-hour token in a new `password_reset_tokens` table, invalidates all existing sessions, logs the user straight into a fresh one). Email links to `/?resetToken=...`; the frontend reads that param on load and shows a "set new password" form. Confirmed live end-to-end on the owner's real account — reset email arrived (via Brevo), they clicked it, set a new password, and it worked; DB checked after and clean (token consumed, exactly one active session).

**Local dev note:** `.claude/settings.local.json` has a `SessionStart` hook that auto-starts the Postgres container, API, and frontend dev server if they're not already running — you shouldn't need to start them by hand unless that hook is missing or disabled. Local dev's seed user is `dev@example.com` (unclaimed — sign up with that email once to set a password), and `DEMO_USER_EMAIL` is unset by default locally, so the logged-out view is empty unless you set it.
